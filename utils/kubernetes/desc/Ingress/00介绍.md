```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-ingress
  annotations:
    # 根据所使用的Ingress Controller，可能需要添加额外的注解
    kubernetes.io/ingress.class: "nginx" # 如果Ingress Controller需要的话
    # 例如，对于NGINX Ingress Controller，可能有更多配置如：
    # nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx # 自 Kubernetes 1.18 起推荐使用
  tls:
  - hosts:
    - www.example.com
    secretName: tls-secret # 需要在Kubernetes中预先创建的TLS证书密钥
  rules:
  - host: www.example.com
    http:
      paths:
      - path: /api/v1
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              name: http
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
```
* tls: 配置了TLS加密，指定了哪些主机名需要使用HTTPS，并引用了一个预先创建的Kubernetes Secret（在这个例子中是tls-secret），该Secret包含了TLS证书和私钥。
* annotations: 这里只展示了一个基本的示例注解，实际使用中根据Ingress Controller的需求可能会有更多配置，比如重定向规则、CORS策略等。
* backend.service: 指定了每个路径应路由到的后端Service及其端口。可以通过名称引用服务，并指定端口名称或端口号


##### pathType配置
1、Prefix:
* 含义: 请求的URL路径必须以指定的路径前缀开始。这是最常用的匹配类型，适用于大多数路由场景。
* 示例: 如果path: /api且pathType: Prefix，那么所有以/api开头的请求（如/api/users或/api/v1/resources）都会被匹配

2、Exact：
* 含义: 请求的URL路径必须与指定的路径完全匹配。这种类型适用于需要精确路径匹配的场景。
* 示例: 如果path: /login且pathType: Exact，只有访问/login的请求会被匹配，而/login/process则不会

3、 ImplementationSpecific:
* 含义: 匹配行为取决于Ingress Controller的具体实现。这意味着不同的Ingress Controller可能会有不同的处理方式。
* 使用: 当不明确指定Prefix或Exact时，某些情况下可能会默认为此类型，但最佳实践是明确指定所需的匹配类型
